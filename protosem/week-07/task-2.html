Section 01

Overview

Objective

Understand how a centralized cloud dashboard can communicate bidirectionally with an ESP32 microcontroller using the MQTT protocol, supporting remote hardware actuation and telemetry synchronization.

Problem Being Addressed

While Task 1 proved local hardware actuation, local web servers suffer from critical architectural constraints: the controlling browser must be on the exact same local Wi-Fi subnet. Devices hidden behind home NAT firewalls or cellular modems cannot be contacted from the wider internet without complex, insecure port-forwarding or dynamic DNS configurations. Task 2 addresses this constraint by introducing a centralized cloud broker that decouples the sender and receiver.

Summary & Expected Purpose

I connected the ESP32 to the Adafruit IO cloud platform using the MQTT protocol. Adafruit IO hosts a graphical cloud dashboard with switch widgets and telemetry feeds. When a user toggles a switch on the dashboard, Adafruit IO publishes an MQTT message to the topic feed. The ESP32, which maintains a persistent lightweight TCP connection to the cloud broker, receives the incoming packet instantly and actuates its GPIO output pin.

Section 02

Concepts

Transitioning from direct HTTP to cloud-based publish-subscribe architectures introduces several core IoT concepts:

Role of Adafruit IO in IoT

Adafruit IO is an open cloud service designed specifically for Internet of Things projects. It provides managed MQTT and REST endpoints, feed databases for time-series logging, and modular UI dashboard blocks (toggles, gauges, sliders, line charts).

MQTT Protocol: Broker, Publisher & Subscriber

MQTT (Message Queuing Telemetry Transport) is a lightweight publish-subscribe messaging transport protocol designed for constrained devices with limited bandwidth and battery power:

  • Broker: Central server (io.adafruit.com) that routes incoming messages to interested clients.
  • Publisher: Any entity sending data to a named topic (e.g., the cloud dashboard publishing an ON state).
  • Subscriber: Any entity listening to a topic (e.g., the ESP32 listening for state transitions).

MQTT Topics & Feeds

Messages are organized into hierarchical slash-delimited strings called topics. In Adafruit IO, each feed maps directly to an MQTT topic formatted as username/feeds/feed-name (e.g., sairam/feeds/led-control). Clients can subscribe to one or multiple feeds simultaneously.

Section 03

System Design

The architecture shifts from point-to-point HTTP to broker-mediated pub/sub messaging:

Primary Cloud Actuation Flow
1 Adafruit IO Dashboard
2 MQTT Message (Topic Feed)
3 ESP32 Microcontroller
4 GPIO Pin Actuation
5 Hardware Response (LED)
Bidirectional Telemetry Loop

When supported by firmware, the ESP32 can also act as an MQTT Publisher, broadcasting sensor values or confirmation ACKs back to a telemetry feed (e.g., username/feeds/device-status) so the cloud dashboard always reflects physical reality.

Component Roles in Pub/Sub Architecture

Component Role Communication Function
Cloud Dashboard User Interface & Publisher Provides interactive toggle controls rendered over HTTPS; publishes state changes to feed.
Adafruit IO Broker MQTT Broker (Port 1883/8883) Maintains feed history, enforces authentication, and distributes payloads to subscribers.
ESP32 Client Subscriber / Actuator Maintains outbound TCP keep-alive connection, decodes incoming packets, and drives GPIO pins.
LED Circuit Physical Hardware Physically switches state according to cloud instructions with zero port forwarding required.

Section 06

Implementation

Below is the complete C++ firmware using the official Adafruit_MQTT_Client library:

ESP32_AdafruitIO_MQTT.ino 
#include <WiFi.h>
#include "Adafruit_MQTT.h"
#include "Adafruit_MQTT_Client.h"

// Wi-Fi Configuration
#define WLAN_SSID       "YOUR_WIFI_SSID"
#define WLAN_PASS       "YOUR_WIFI_PASSWORD"

// Adafruit IO Broker Configuration
#define AIO_SERVER      "io.adafruit.com"
#define AIO_SERVERPORT  1883
#define AIO_USERNAME    "YOUR_AIO_USERNAME"
#define AIO_KEY         "YOUR_AIO_KEY"

// Pin definition
const int ledPin = 2;

// Create Wi-Fi and MQTT Client instances
WiFiClient client;
Adafruit_MQTT_Client mqtt(&client, AIO_SERVER, AIO_SERVERPORT, AIO_USERNAME, AIO_KEY);

// Setup subscription feed for 'led-control'
Adafruit_MQTT_Subscribe ledControl = Adafruit_MQTT_Subscribe(&mqtt, AIO_USERNAME "/feeds/led-control");

// Helper function to maintain MQTT broker connection
void MQTT_connect();

void setup() {
  Serial.begin(115200);
  pinMode(ledPin, OUTPUT);
  digitalWrite(ledPin, LOW);

  // Connect to Wi-Fi
  Serial.print("Connecting to Wi-Fi ");
  WiFi.begin(WLAN_SSID, WLAN_PASS);
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.println("\nWiFi connected! IP: " + WiFi.localIP().toString());

  // Subscribe to the Adafruit IO feed
  mqtt.subscribe(&ledControl);
}

void loop() {
  // Ensure MQTT connection is active
  MQTT_connect();

  // Read subscription packets with 5000ms timeout
  Adafruit_MQTT_Subscribe *subscription;
  while ((subscription = mqtt.readSubscription(5000))) {
    if (subscription == &ledControl) {
      Serial.print("Received MQTT Feed Update: ");
      char *payload = (char *)ledControl.lastread;
      Serial.println(payload);

      // Actuate hardware based on payload string
      if (strcmp(payload, "1") == 0 || strcmp(payload, "ON") == 0) {
        digitalWrite(ledPin, HIGH);
        Serial.println("Action: LED switched ON");
      } 
      else if (strcmp(payload, "0") == 0 || strcmp(payload, "OFF") == 0) {
        digitalWrite(ledPin, LOW);
        Serial.println("Action: LED switched OFF");
      }
    }
  }

  // Ping broker to maintain keep-alive
  if (!mqtt.ping()) {
    mqtt.disconnect();
  }
}

// Function to handle connection and automatic reconnections
void MQTT_connect() {
  int8_t ret;
  if (mqtt.connected()) return;

  Serial.print("Connecting to Adafruit IO MQTT Broker... ");
  uint8_t retries = 3;

  while ((ret = mqtt.connect()) != 0) {
    Serial.println(mqtt.connectErrorString(ret));
    Serial.println("Retrying connection in 5 seconds...");
    mqtt.disconnect();
    delay(5000);
    retries--;
    if (retries == 0) {
      Serial.println("Failed to connect after retries. Pausing.");
      while (1);
    }
  }
  Serial.println("MQTT Broker Connected!");
}

How Communication Works

  • Keep-Alive Persistence: The ESP32 maintains an open TCP socket using mqtt.ping(), preventing intermediate NAT routers from closing the tunnel.
  • Non-Blocking Event Listening: mqtt.readSubscription(5000) listens for incoming broker packets without flooding the processor.
  • Payload Processing: Incoming text payloads ("1" or "0") are compared using strcmp(), triggering immediate GPIO writes.

Configuration

Follow these configuration steps to authenticate with Adafruit IO:

Credential Security Best Practices

Never commit raw credentials to version control. In our repository sketches, credentials are parameterized as: 

// Sensitive credentials configured via config.h or environment variables
#define AIO_USERNAME    "YOUR_AIO_USERNAME"
#define AIO_KEY         "YOUR_AIO_KEY"

Setup Checklist

  1. Install Adafruit MQTT Library via Arduino IDE Library Manager.
  2. Confirm your Adafruit IO username is exact (case-sensitive).
  3. Verify feed name: Adafruit IO generates an internal slug like led-control even if you entered "LED Control". Always use the slug.
  4. Open Serial Monitor at 115200 baud to confirm successful broker authentication.

Section 09

Challenges & Fixes

Problem Broker returned "Connection Error: RC 4" (Bad Credentials) during mqtt.connect().
Investigation Checked the Adafruit IO console and found that my account password was mistakenly used instead of the dedicated AIO Active Key.
Solution Regenerated the dedicated Adafruit IO API Key and updated AIO_KEY in the sketch.
Outcome Broker returned RC 0 (Connection Accepted) and immediately acknowledged feed subscriptions.
Problem ESP32 stopped receiving messages after being idle for approximately 3 minutes.
Investigation Adafruit IO MQTT broker terminates client sockets if no keep-alive ping or publish occurs within the timeout threshold.
Solution Added periodic mqtt.ping() invocation within the main execution loop and automated reconnect handling in MQTT_connect().
Outcome Zero connection drops over continuous overnight test runs.

Reflection

Future Improvements

In future iterations, upgrading from unencrypted TCP port 1883 to SSL/TLS encrypted MQTTS on port 8883 using WiFiClientSecure would ensure all payloads, authentication keys, and telemetry streams are protected against interception across public transit networks.
